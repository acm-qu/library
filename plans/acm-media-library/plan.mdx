# QU ACM Media Library: build and deploy plan

**Objective.** Ship a library for the chapter's event photos and videos. Member-tier items are **public**: anyone can browse events, view fast WebP copies, stream videos at 360p / 720p / 1080p and download originals without signing in (the UI labels this tier "Public"). Every account is a core account, and signing in with an emailed code shows core-tier content (encrypted at rest), lets the core team upload after events and edit events. Admin is a flag on top of core: admins delete events and manage members, the processing queue, tone-curve overrides and storage. Everything runs on the single shared cPanel account `quhosting@qu.hosting.acm.org`.

**Sources.** The backend contract is `handoff-backend.md`, which is treated as requirements wherever it says *Decided*. The UI is the **Darkroom Archive** design on the Claude Design canvas *QU ACM Media Library* (30 artboards: desktop browse, upload and admin screens; phone screens in English and Arabic; system states; design system v1), with screen requirements from `handoff-design.md`. The design already exists, so the UI is built straight from it instead of from the interim UI the backend handoff describes. The handoff's layering rule still applies: pages never call `fetch` themselves.

**Done means:**
- Every screen group in the design runs against the real API, on phone and desktop, in light and dark themes. The Arabic boards follow the Arabic decision in Decisions taken.
- A real event flows through the system: upload 80 photos and 3 videos from a phone, close the tab, resume, wait for processing, then watch signed out. HLG iPhone footage is tone-mapped to SDR.
- Core-tier files are encrypted on disk and still stream and download with HTTP Range.
- The app is live on the production subdomain, with a cron-driven worker, nightly backups and docs (`docs/HANDOFF.md`, `docs/ops.md`, `docs/security.md`, `CLAUDE.md`).
- All Vitest and pytest suites pass, plus a scripted smoke test against production.

The decisions taken are listed at the bottom. The two questions that were open (OTP sender and build location) are now settled, and **Open Questions** records the answers.

### One event, end to end

The day after the chapter's hackathon, a core member opens **Upload** on their phone over campus Wi-Fi. They create "Hackathon, day 1", select 80 photos and 3 iPhone videos, and the files start uploading in resumable 8 MiB chunks, two at a time and never more than one video at once. They lock the phone; when they come back, a banner says "Resume 3 unfinished uploads", they pick the same files, and the uploads continue from where they stopped. The done screen says photos will be ready in a few seconds and videos in about 44 minutes. That estimate is possible because ingest already probed each video: 34 minutes of HLG footage at about 1.2× processing time, plus a minute of setup per video. Photos are ready in seconds because image jobs always run ahead of video jobs.

Behind that, each finished upload becomes an `assets` row plus a `jobs` row, and the API starts the worker straight away (`WORKER_WAKE`); cron every 2 minutes is the safety net. The worker takes one job at a time:
- Pillow writes `view.webp` and `thumb.webp`.
- ffmpeg decodes each video once, tone-maps it, and writes a three-rung HLS ladder in single-file mode.
- Core-tier outputs are sealed with per-asset keys.

That evening a chapter member opens the event on a laptop without signing in. They read as the anonymous member viewer, so they see only member-tier ("Public"), ready items without uploader names, and event counts include only what they can see. The video starts on Auto at 720p and switches to 1080p when they pick it, with every byte served through `/api/media/*` after a permission check.

<Callout id="pg96-decision" tone="decision">

**Database: the cPanel-managed cluster, with a schema limited to PostgreSQL 9.6 features.** The visible client tools are 9.6, and a cPanel account can't run `CREATE EXTENSION`, so the schema avoids anything newer or extension-based:
- **Statuses and roles:** `text` columns with `CHECK` constraints instead of enums. Adding an enum value can't run inside a migration transaction before PG 12, and drizzle-kit wraps each migration in one.
- **Ids:** UUID v7 generated in the app (`uuidv7` npm). No `gen_random_uuid()` or `pgcrypto`.
- **Emails:** `email text UNIQUE` plus `CHECK (email = lower(email))`. The app lower-cases emails on the way in. A plain unique column is used instead of an expression index because `ON CONFLICT (email) DO NOTHING` (bulk add) can't target an expression index. No `citext`.
- **Search:** an expression GIN index on `to_tsvector('simple', title || ' ' || coalesce(description,''))`, built into core since 8.3, plus `ILIKE` prefix matching for short queries. No `pg_trgm` and no generated columns.
- **Auto-increment:** `bigserial` instead of identity columns.
- **Job claim:** `FOR UPDATE SKIP LOCKED` (available since 9.5).

This is a strict subset of modern Postgres, so the same migrations run on a newer cluster unchanged. Local development and CI use a `postgres:9.6` container, so what passes locally passes in production.

**Tooling rules that follow from 9.6:**
- Only `drizzle-kit generate` is allowed. `push`, `pull`, `check` and `studio` read catalog columns added in PG 10–12 and fail against the server.
- Migrations run through a small bundled script using `drizzle-orm/node-postgres/migrator`, so production doesn't need drizzle-kit.
- **Banned:** identity and `GENERATED` columns, `INCLUDE` indexes, `websearch_to_tsquery` (use `plainto_tsquery`), `jsonb_path_*`, `gen_random_uuid`, procedures, and declarative partitioning.
- Auth is md5 (9.6 has no SCRAM), which node-postgres supports.
- At boot, the API refuses to start unless `server_version_num` is at least 90500 (9.5), which `SKIP LOCKED` and `ON CONFLICT` need.



</Callout>

<Callout id="pg96-risk" tone="risk">

PostgreSQL 9.6 has been end-of-life since November 2021 and gets no security fixes. The exposure is limited: the database listens only on the local socket or loopback, the app connects with a password over the cPanel-managed `pg_hba`, and nothing outside the host can reach it. `docs/ops.md` records this so the chapter can ask ACM HQ about an upgrade. No code change is needed when that happens.

</Callout>

**Why this shape.** The host limits drive it. Passenger owns the HTTP process, so the API can't also run long background work: Passenger may recycle it, and CPU spent there counts against the same 4 cores. That's why processing runs in a separate worker under `flock`: the API starts it as soon as an upload finishes (`WORKER_WAKE`, the crontab's command with `flock -w 20`, so a running worker picks the job up and one that is exiting is waited out), and cron every 2 minutes covers admin actions, retries and crashes. The host allows 150 entry processes, and polling every 15 seconds is enough for live status, so there is no SSE or WebSocket in v1. Media never sits in a public directory: Apache serves only the built SPA via Passenger, and every media byte goes through `canView`, including for signed-out visitors.

<Callout id="deploy-decision" tone="decision">

**Settled: build on the laptop and ship artifacts with rsync.** The handoff's §13 says to build on the server; the app does the reverse.
- The API, worker and migrator are each bundled with esbuild into a single file, with only `pg` and `sodium-native` left external.
- The build emits a **generated minimal `package.json` and lockfile** with just those two dependencies, so the server's `node_modules` holds a few hundred files. Installing the whole workspace would pull in React, hls.js and Uppy, about 30,000 files.
- A build on the laptop can't fight live traffic for CPU, threads or the 4 GB of memory.

`scripts/deploy.sh`:
1. `npm run build`.
2. `rsync` to `releases/<sha>`.
3. `npm ci` of the minimal manifest, run in the cPanel Node 24 venv so `sodium-native` picks its linux-x64 prebuild.
4. Only when `py/` or the gate changed (hash in `shared/.py-hash`): rebuild the worker venv, scorer weights and tone-curve gate at low priority (nice 19, ionice -c3), with pinned versions and no `pip --upgrade`.
5. `node migrate.js` (bundled migrator).
6. Flip the `current` symlink, then restart the app process (see `docs/ops.md`).
7. `curl /api/health` until the new release's sha appears.

Migrations are **additive only** (expand, then contract in a later release), because they run while the old code is still serving and rollback only re-points the symlink. Passenger is pinned to **one application process**: tus's default locker and the rate-limit counters are in memory. Which directive CloudLinux allows in `.htaccess` (`PassengerMaxInstances 1` or the app-level pool setting) is checked in Milestone 0. Running more processes later would need a Postgres advisory-lock tus locker and a Postgres-backed rate-limit store.

</Callout>

**Client IPs and rate limits behind the proxy.** Apache hands every request to Passenger from loopback, so Fastify runs with `trustProxy: '127.0.0.1'` and reads the client address from `X-Forwarded-For`. Without that, every per-IP limit would apply to the whole site, and `sessions.ip` would always be 127.0.0.1. Limits per client IP:
- **Auth:** the handoff's numbers plus a daily cap. request-code 3 per 15 minutes and 10 per day per email (at most 50 guesses a day for one address, however many IPs try) and 10 per hour per IP; verify 20 per 15 minutes per IP.
- **Global:** 600 requests per minute for `/api/*`, which absorbs a whole campus room behind one NAT address.
- **Exempt from the global limit:** `/api/uploads/*` (core only), and `/api/media/*` for signed-in viewers. HLS byte ranges and 8 MiB PATCHes would otherwise use it up. Media is public for the member tier, so signed-out media requests share the global per-IP limit.

## Low-level design

### Data model

The table set follows the backend handoff, adjusted for 9.6: `text` with `CHECK` instead of enums, a lower-cased unique `email` instead of `citext`, and ids from the app. Every table keeps the handoff's `created_at`, and events and assets keep `updated_at` too (omitted from the cards below for space). There are four additions:
- `assets.duplicate_of` lets the upload UI warn about re-uploads.
- `assets.rendition_rev` drives cache busting.
- `jobs.priority` backs both kind-based ordering and "Move to the top".
- `jobs.outcome` records a job that finished by sending its asset to review.
- `users.gender` (nullable, check male|female) is asked for on first sign-in, together with the name.
- `access_requests` holds "Request access" submissions from the sign-in screen until an admin approves or rejects them.

Indexes that matter for the hot paths:
- `assets (event_id, tier, status) WHERE deleted_at IS NULL` serves event grids.
- `assets (event_id, original_sha256)` serves duplicate detection.
- `jobs (state, priority DESC, created_at)` serves the job claim.
- `otp_codes (email, created_at DESC)` serves verification.
- `events` gets a GIN index on the FTS expression for search, and `(starts_on DESC, id)` for cursor pagination.
- Event grids sort by `coalesce(captured_at, created_at), id`, with a matching expression index. That key doubles as the cursor, because `captured_at` is often missing.

Delete behaviour and per-viewer fields:
- **Foreign keys.** `events.cover_asset_id`, `assets.duplicate_of` and `jobs.asset_id` are `ON DELETE SET NULL`, so a purge job can delete its asset row without cascading into its own job row. `renditions`, `processing_runs` and `asset_keys` cascade.
- **Event covers.** A cover is resolved per viewer. If the chosen cover isn't visible to this viewer (core tier, or unfinished), the first visible photo is used instead, and `coverAssetId` is returned only when the viewer can see it, so a hidden core cover never reveals that the item exists. The web app no longer picks covers or shows a cover banner on the event page: Library cards show the automatic cover (`coverUrl`), and the API's cover logic and column are unchanged.
- **Core-content marker.** `GET /events` returns `hasCoreContent` only to core viewers, for the design's core-only marker.



### Who can see what: `canView`

Every media route, asset read and HLS key request goes through one pure function, `access(viewer, asset)`. It returns a level, and each route declares the minimum level it needs:
- `/media/:id/original` needs at least `download`.
- Thumbnails, view copies, posters, HLS and the key need `full`.
- Lists and `/assets/:id` need at least `status`.

Anything below the route's minimum is **404**, never 403. The design repeats this rule: signed-out visitors never learn that core items exist.

Read routes need no sign-in. `readerOf()` in `apps/api/src/auth/plugin.ts` turns a request without a session into `ANON`, an active member-role viewer that matches no uploader, so member-tier items are public and everything else follows the same table. Account, upload and admin routes still need a core session. There are no member accounts any more: every account is core, admin is a flag on top, and an old member row can't sign in.

- **Upload rows exist from the start.** `onUploadCreate` inserts the `uploading` row, keyed by the tus id in `assets.upload_id`, so My uploads and the "Resume N unfinished uploads" banner come from the server instead of one browser's localStorage. Each chunk marks the row alive; one untouched for an hour stops counting as active. The hourly cleanup deletes `uploading` rows and their tus files after 48 hours.
- **Ready items stay ready during re-processing.** Re-processing, a curve override or a tier change never takes a ready item offline. The job writes into a fresh output directory (`r{rev}/` under the asset directory), then swaps the rendition rows and bumps `rendition_rev` in one transaction, then deletes the old directory. Viewers keep playing the old outputs until the swap. Core members and admins see a "processing" badge, derived from the job, while it runs.
- **Tier changes take effect at once.** A member → core change hides the item from signed-out visitors immediately, because `access()` reads the tier, not the files.
- **What "Process anyway" does depends on the review reason:**
  - Log or unknown-transfer video: encode as SDR with bt709 tags and no tone mapping. The admin can re-process with a curve afterwards.
  - True-HDR still: Pillow converts it to 8-bit sRGB with clipping.
  - Unrecognised container: not offered; only "Keep original only" is.

### Sign-in

Unknown and disabled emails, and old member rows (only core accounts sign in), get a decoy code row. Without it, an unknown email could only ever return "expired" from verify, never "wrong code, 3 attempts left", and that difference would reveal who is registered. A decoy can never verify, because its hash matches no code and verify also re-checks `status = 'active'`.

**Request access.** The Login screen links to a small form (email, name, gender). `POST /auth/request-access` takes the CSRF header, is limited to 5 an hour per IP and 3 a day per email, and always answers 204 after the same timing floor as request-code. It inserts a pending `access_requests` row only when the email is neither a user nor already pending (the partial unique index settles races), so the answer never reveals who has an account. Admins see pending requests under Admin › Members › Requests. Approve creates an active, non-admin core user with the request's name and gender in one transaction, marks the request approved and writes `audit_log` (409 if that email became a user meanwhile); the "You've been approved" mail with a link to `/login` goes out after the response. Reject only marks the request and audits it.

**First sign-in.** A signed-in person whose name is empty or gender is null completes their profile first. The web shell redirects every signed-in screen to `/welcome?next=…` (signed-out visitors are unaffected), and Continue PATCHes `/me` and goes on to `next`. The API enforces it too: `requireCore` and `requireAdmin` answer 409 `profile_incomplete`, and `readerOf()` treats the person as ANON, so public reads keep working but core items stay hidden. `/me` (GET and PATCH) and `/auth/*` keep working. While `PRELAUNCH_ALLOWLIST` is set, only allowlisted addresses can sign in, approved or not.

Sessions slide: each authenticated request refreshes `expires_at` at most once an hour and `last_seen_at` at most every 5 minutes, so reads don't turn into a write per request. Signing in drops any session the browser already held (another user on a shared PC). Logging out deletes one session row. "Sign out of all devices", and disabling a user, delete all of that user's rows.

### Resumable upload

<Mermaid

**The final PATCH does no full pass over the file.** At the host's 30 MB/s I/O limit, hashing a 3 GB clip takes about 100 seconds, so it can't happen inside an HTTP request. The finish hook therefore only:
- sniffs the first 4 KB;
- runs a header-only probe;
- renames the file (same filesystem, so no data copy);
- commits the asset and job rows.

The probe fills `duration_s`, `hdr`, `width` and `height` straight away, which is what makes the done-screen ETA and the grid's placeholder sizes possible.

SHA-256 is the worker's first step for every job. A match within the same event sets `duplicate_of`, and the upload and My uploads screens show the duplicate warning from the next poll.

**Resume on phones.** Re-picking from the iOS photo library can change a file's name and `lastModified`, which defeats Uppy's fingerprint. So the resume banner matches re-picked files to the event's `uploading` rows by original filename and size, and continues with that row's tus id. The file input's `accept` lists `image/heic` and `video/quicktime`, so iOS sends originals instead of transcoding them. Milestone 4 checks this on a real iPhone: originals must arrive byte-identical, and HLG must survive.

**Two uploads at a time, at most one video.** The host's disk IO is capped at 30 MB/s, so the client starts up to two files in parallel and never two videos at once.

Each step writes `jobs.step` (for example "Scoring tone curves" or "Encoding 720p") and `jobs.progress`, which ffmpeg's `-progress pipe:1` provides as `out_time_ms` ÷ duration. These are the strings the queue and My uploads screens show. A child process is killed, with its process tree, after 3 × its expected cost, with a 10-minute minimum. Every child gets thread caps (`OMP_NUM_THREADS` and friends, and explicit `-threads` / `-filter_threads` on every ffmpeg and ffprobe call), because the host reports 64 CPUs while CloudLinux counts every thread against the account's 200 tasks.

- **Queue order.** Image, retier and purge jobs get priority 100 and videos get 0, so photos are never stuck behind a two-hour recording. "Move to the top" sets a job's priority to the current maximum + 1. The ETA function walks jobs in exactly this claim order.
- **Attempts.** A crash costs one attempt, not two. The claim increments `attempts`; the stale reset puts the job straight back in the queue without incrementing. A stale job already at `max_attempts` becomes `failed`, and so does its asset.
- **Cancel.** Cancelling a queued job sets it `cancelled` straight away. For a running job, the worker checks `jobs.state` every 5 seconds while a child runs; on `cancelled` it kills the process tree and deletes `tmp/`. A first-time process job then leaves its asset `failed` with the message "Cancelled by an admin". A re-process job leaves the ready asset untouched.
- **Retry** resets `attempts` to 0 and `run_after` to now. The uploader can retry through `POST /uploads/:assetId/retry`, admins through `/admin/jobs/:id/retry`.

### ETA

The handoff's formula is implemented once in `packages/core/eta.ts` and used by both the API (My uploads, the queue) and the worker (`jobs.est_seconds`):

<Code
  id="eta-code"
  filename="packages/core/src/eta.ts"
  language="ts"
  code={"export type Rho = { sdr: number; hdr: number; hdrFixed?: number };\nexport const DEFAULT_RHO: Rho = { sdr: 0.6, hdr: 1.2 };\nexport const RHO_RANGE = [0.3, 3] as const;   // learned rho stays in these bounds\nexport const SCORE_RANGE = [60, 900] as const; // learned score_seconds too\n\nexport function jobCost(j: EtaJob, rho: Rho): number {\n  if (j.kind === 'image') return IMAGE_SECONDS;\n  const d = j.durationS ?? 0;\n  return isHdr(j.hdr) ? rho.hdr * d + (rho.hdrFixed ?? HDR_FIXED_SECONDS) : rho.sdr * d;\n}\n\n/** Seconds until each job finishes, in claim order (running job first, scaled by its remaining progress). */\nexport function queueEtas(ordered: EtaJob[], rho: Rho): number[] {\n  let t = 0;\n  return ordered.map((j) => (t += jobCost(j, rho) * (1 - clamp01(j.progress ?? 0))));\n}\n\nexport function nextRho(current: number, encodeS: number, durationS: number): number {\n  if (!(durationS > 0) || !(encodeS >= 0)) return current;\n  return clamp(RHO_RANGE, (1 - RHO_ALPHA) * current + RHO_ALPHA * (encodeS / durationS));\n}\n"}
/>

After each video job, the worker updates `rho_sdr` or `rho_hdr` in `app_settings` with an exponential moving average (α = 0.2) of measured *encode* time ÷ duration, clamped to [0.3, 3]. Scoring time is excluded: the HDR fixed cost covers it, and when automatic selection runs it is a learned `score_seconds`, clamped to [60, 900]. The clamps stop one throttled or odd run from inflating (or zeroing) every later ETA. Jobs are summed in claim order (priority, then age), the same order the worker uses.

What the API (`apps/api/src/lib/queue.ts`) does with the numbers:
- **Purges** and jobs **waiting out a retry backoff** are left out of the sum; a job in backoff has no ETA.
- **Stale worker.** When the worker heartbeat (`worker_tick`) is older than 5 minutes, every ETA is null and the UI says "Waiting for the processor" instead of a clock that keeps sliding. The worker beats every minute, during long jobs too.
- **Upload screen.** It shows "waiting to start" or "stalled" instead of a huge time.

### Security controls

- **Headers (Helmet):**
  - CSP: `default-src 'self'; media-src 'self' blob:; worker-src 'self' blob:; img-src 'self' blob: data:; font-src 'self'; style-src 'self'; frame-ancestors 'none'`. hls.js needs `blob:` for MediaSource and its worker.
  - `Referrer-Policy: same-origin`.
  - HSTS on.
- **Log redaction.** The pino redaction paths cover `req.headers.cookie`, `set-cookie`, `body.code`, `body.email` on auth routes, and every key-bearing field. The worker never logs `params` that carry key paths. In production the API logs to `LOG_FILE`, because lsnode drops the app's stdout.
- **Sign-in hardening.** A daily per-email code limit on top of the 15-minute one; the browser's old session is dropped on sign-in; rejected codes are logged as `otp_fail` (reason and IP only); every sign-in writes an `auth.login` audit row.
- **Ownership and leaks.** A tus upload id belongs to its uploader (anyone else gets 404); an event's `coverAssetId` is hidden when the viewer can't see that cover; uploader names are hidden from signed-out visitors; signed-out media requests count toward the global rate limit.
- **Secrets.** `.env.example` ships with every variable from the handoff's §12. On the server, `shared/.env` is chmod 600. `MASTER_KEY` is also kept in the chapter's password manager.
- **Ops.** One SSH key per maintainer, cPanel 2FA, and the known Postgres 9.6 exposure, all documented in `docs/ops.md`.

**Public URLs: `/events/:slug` and `/p/:assetId`.**
- **The viewer and player are a modal route.** Opening an item from a grid pushes `/p/:assetId` with the grid as the background location: the back button closes the lightbox and the grid keeps its scroll position. </Callout>

<Callout id="i18n-decision" tone="decision">

</Callout>

<Callout id="jpeg-decision" tone="decision">

</Callout>

Interaction details the artboards imply and the code must honor:
- **Justified grid.** Rows are computed from `width` / `height` before images load, and virtualized with `@tanstack/react-virtual` by row. The next page is fetched when the last virtual row comes within two screens of the viewport. This is how the grid stays smooth at tens of thousands of items.
- **Resume after closing the tab.** The upload screen reads Uppy's stored tus fingerprints at mount. For each one, it compares `HEAD` offsets with the event's server-side assets, and shows "Resume N unfinished uploads" when any remain. Picking the same files continues from the stored offsets.
- **Keyboard.** The lightbox traps focus. Arrow keys, I, Z and Esc are bound to the dialog element, not to `window`. Tables and tabs follow the WAI-ARIA patterns, and `prefers-reduced-motion` disables the shimmer and transitions, matching `app.css`.
- **Alt text.** Alt text falls back to "Photo from ‹event title›, ‹date›" when there is nothing better.
- **Loading and motion.** Every screen has a skeleton loading state and images fade in. Page entrance animates the content only: admin screens share the shell's page key, so the side nav stays still. - **Polling.** Lists that show unfinished work poll every 15 s, and only while something is unfinished.
