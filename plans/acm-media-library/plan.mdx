# QU ACM Media Library: build and deploy plan

**Objective.** Ship a private, login-only library for the chapter's event photos and videos. Members sign in with an emailed code, browse events, view fast WebP copies, stream videos at 360p / 720p / 1080p and download originals. Core members also see core-tier content (encrypted at rest), upload after events and manage events. Admins manage members, the processing queue, tone-curve overrides and storage. Everything runs on the single shared cPanel account `quhosting@qu.hosting.acm.org`.

**Sources.** The backend contract is `handoff-backend.md`, which is treated as requirements wherever it says *Decided*. The UI is the **Darkroom Archive** design on the Claude Design canvas *QU ACM Media Library* (30 artboards: desktop browse, upload and admin screens; phone screens in English and Arabic; system states; design system v1), with screen requirements from `handoff-design.md`. The design already exists, so the UI is built straight from it instead of from the interim UI the backend handoff describes. The handoff's layering rule still applies: pages never call `fetch` themselves.

**Done means:**
- Every screen group in the design runs against the real API, on phone and desktop, in light and dark themes. The Arabic boards follow the Arabic decision in Open Questions.
- A real event flows through the system: upload 80 photos and 3 videos from a phone, close the tab, resume, wait for processing, then watch as a member. HLG iPhone footage is tone-mapped to SDR.
- Core-tier files are encrypted on disk and still stream and download with HTTP Range.
- The app is live on the production subdomain, with a cron-driven worker, nightly backups and docs (`docs/HANDOFF.md`, `docs/ops.md`, `docs/security.md`, `CLAUDE.md`).
- All Vitest and pytest suites pass, plus a scripted smoke test against production.

The decisions taken so far are listed at the bottom, and the two still open are in **Open Questions**.

### One event, end to end

The day after the chapter's hackathon, a core member opens **Upload** on their phone over campus Wi-Fi. They create "Hackathon, day 1", select 80 photos and 3 iPhone videos, and the files start uploading in resumable 8 MiB chunks. They lock the phone; when they come back, a banner says "Resume 3 unfinished uploads", they pick the same files, and the uploads continue from where they stopped. The done screen says photos will be ready in a few seconds and videos in about 44 minutes. That estimate is possible because ingest already probed each video: 34 minutes of HLG footage at about 1.2× processing time, plus a minute of setup per video. Photos are ready in seconds because image jobs always run ahead of video jobs.

Behind that, each finished upload becomes an `assets` row plus a `jobs` row. A cron-started worker takes one job at a time:
- Pillow writes `view.webp` and `thumb.webp`.
- ffmpeg decodes each video once, tone-maps it, and writes a three-rung HLS ladder in single-file mode.
- Core-tier outputs are sealed with per-asset keys.

That evening a member opens the event on a laptop. They see only member-tier, ready items, and event counts include only what they can see. The video starts on Auto at 720p and switches to 1080p when they pick it, with every byte served through `/api/media/*` after a permission check.

<Callout id="pg96-decision" tone="decision">

**Database: the cPanel-managed cluster, with a schema limited to PostgreSQL 9.6 features.** The visible client tools are 9.6, and a cPanel account can't run `CREATE EXTENSION`, so the schema avoids anything newer or extension-based:
- **Statuses and roles:** `text` columns with `CHECK` constraints instead of enums. Adding an enum value can't run inside a migration transaction before PG 12, and drizzle-kit wraps each migration in one.
- **Ids:** UUID v7 generated in the app (`uuidv7` npm). No `gen_random_uuid()` or `pgcrypto`.
- **Emails:** `email text UNIQUE` plus `CHECK (email = lower(email))`. The app lower-cases emails on the way in. A plain unique column is used instead of an expression index because `ON CONFLICT (email) DO NOTHING` (bulk add) can't target an expression index. No `citext`.
- **Search:** an expression GIN index on `to_tsvector('simple', title || ' ' || coalesce(description,''))`, built into core since 8.3, plus `ILIKE` prefix matching for short queries. No `pg_trgm` and no generated columns.
- **Auto-increment:** `bigserial` instead of identity columns.
- **Job claim:** `FOR UPDATE SKIP LOCKED` (available since 9.5).

This is a strict subset of modern Postgres, so the same migrations run on a newer cluster unchanged. Local development and CI use a `postgres:9.6` container, so what passes locally passes in production.

**Tooling rules that follow from 9.6:**
- Only `drizzle-kit generate` is allowed. `push`, `pull`, `check` and `studio` read catalog columns added in PG 10–12 and fail against the server.
- Migrations run through a small bundled script using `drizzle-orm/node-postgres/migrator`, so production doesn't need drizzle-kit.
- **Banned:** identity and `GENERATED` columns, `INCLUDE` indexes, `websearch_to_tsquery` (use `plainto_tsquery`), `jsonb_path_*`, `gen_random_uuid`, procedures, and declarative partitioning.
- Auth is md5 (9.6 has no SCRAM), which node-postgres supports.
- At boot, the API refuses to start unless `server_version_num` is at least 90500 (9.5), which `SKIP LOCKED` and `ON CONFLICT` need.



</Callout>

<Callout id="pg96-risk" tone="risk">

PostgreSQL 9.6 has been end-of-life since November 2021 and gets no security fixes. The exposure is limited: the database listens only on the local socket or loopback, the app connects with a password over the cPanel-managed `pg_hba`, and nothing outside the host can reach it. `docs/ops.md` records this so the chapter can ask ACM HQ about an upgrade. No code change is needed when that happens.

</Callout>

**Why this shape.** The host limits drive it. Passenger owns the HTTP process, so the API can't also run long background work: Passenger may recycle it, and CPU spent there counts against the same 4 cores. That's why processing runs in a separate cron-started worker under `flock`. The host allows 150 entry processes, and polling every 5 seconds is enough for live status, so there is no SSE or WebSocket in v1. Media never sits in a public directory: Apache serves only the built SPA via Passenger, and every media byte goes through `canView`.

<Callout id="deploy-decision" tone="decision">

**Recommended (needs your call, see Open Questions): build on the laptop and ship artifacts with rsync.** The handoff's §13 says to build on the server; this plan recommends the reverse.
- The API, worker and migrator are each bundled with esbuild into a single file, with only `pg` and `sodium-native` left external.
- The build emits a **generated minimal `package.json` and lockfile** with just those two dependencies, so the server's `node_modules` holds a few hundred files. Installing the whole workspace would pull in React, hls.js and Uppy, about 30,000 files.
- A build on the laptop can't fight live traffic for CPU, threads or the 4 GB of memory.

`scripts/deploy.sh`:
1. `npm run build`.
2. `rsync` to `releases/<sha>`.
3. `npm ci` of the minimal manifest, run in the cPanel Node 24 venv so `sodium-native` picks its linux-x64 prebuild.
4. `node migrate.js` (bundled migrator).
5. Flip the `current` symlink, then `touch tmp/restart.txt`.
6. `curl /api/health` until the new release's sha appears.

Migrations are **additive only** (expand, then contract in a later release), because they run while the old code is still serving and rollback only re-points the symlink. Passenger is pinned to **one application process**: tus's default locker and the rate-limit counters are in memory. Which directive CloudLinux allows in `.htaccess` (`PassengerMaxInstances 1` or the app-level pool setting) is checked in Milestone 0. Running more processes later would need a Postgres advisory-lock tus locker and a Postgres-backed rate-limit store.

</Callout>

**Client IPs and rate limits behind the proxy.** Apache hands every request to Passenger from loopback, so Fastify runs with `trustProxy: '127.0.0.1'` and reads the client address from `X-Forwarded-For`. Without that, every per-IP limit would apply to the whole site, and `sessions.ip` would always be 127.0.0.1. Limits per client IP:
- **Auth:** the handoff's numbers. request-code 3 per 15 minutes per email and 10 per hour per IP; verify 20 per 15 minutes per IP.
- **Global:** 600 requests per minute for `/api/*`, which absorbs a whole campus room behind one NAT address.
- **Exempt from the global limit:** `/api/media/*` and `/api/uploads/*`. HLS byte ranges and 8 MiB PATCHes would otherwise use it up, and both routes are already authenticated.

## Low-level design

### Data model

The table set follows the backend handoff, adjusted for 9.6: `text` with `CHECK` instead of enums, a lower-cased unique `email` instead of `citext`, and ids from the app. Every table keeps the handoff's `created_at`, and events and assets keep `updated_at` too (omitted from the cards below for space). There are four additions:
- `assets.duplicate_of` lets the upload UI warn about re-uploads.
- `assets.rendition_rev` drives cache busting.
- `jobs.priority` backs both kind-based ordering and "Move to the top".
- `jobs.outcome` records a job that finished by sending its asset to review.

Indexes that matter for the hot paths:
- `assets (event_id, tier, status) WHERE deleted_at IS NULL` serves event grids.
- `assets (event_id, original_sha256)` serves duplicate detection.
- `jobs (state, priority DESC, created_at)` serves the job claim.
- `otp_codes (email, created_at DESC)` serves verification.
- `events` gets a GIN index on the FTS expression for search, and `(starts_on DESC, id)` for cursor pagination.
- Event grids sort by `coalesce(captured_at, created_at), id`, with a matching expression index. That key doubles as the cursor, because `captured_at` is often missing.

Delete behaviour and per-viewer fields:
- **Foreign keys.** `events.cover_asset_id`, `assets.duplicate_of` and `jobs.asset_id` are `ON DELETE SET NULL`, so a purge job can delete its asset row without cascading into its own job row. `renditions`, `processing_runs` and `asset_keys` cascade.
- **Event covers.** A cover is resolved per viewer. If the chosen cover isn't visible to this viewer (core tier, or unfinished), the first visible photo is used instead.
- **Core-content marker.** `GET /events` returns `hasCoreContent` only to core viewers, for the design's core-only marker.



### Who can see what: `canView`

Every media route, asset read and HLS key request goes through one pure function, `access(viewer, asset)`. It returns a level, and each route declares the minimum level it needs:
- `/media/:id/original` needs at least `download`.
- Thumbnails, view copies, posters, HLS and the key need `full`.
- Lists and `/assets/:id` need at least `status`.

Anything below the route's minimum is **404**, never 403. The design repeats this rule: members never learn that core items exist.

### Asset lifecycle

<Mermaid
  id="asset-states"
  caption="Asset status transitions. Every arrow out of processing is written by the worker; every admin arrow writes an audit_log row."
  source={`stateDiagram-v2
  [*] --> uploading: tus POST · onUploadCreate inserts the row
  uploading --> queued: onUploadFinish · magic bytes OK · quick probe · process job

  needs_review --> original_only: Keep original only (admin)
  ready --> ready: re-process · curve override · tier change (job runs beside it, outputs swap atomically)
  ready --> deleting: Delete (admin)
  failed --> deleting

  original_only --> deleting
  deleting --> [*]: purge job removes files + rows`}
/>

- **Upload rows exist from the start.** `onUploadCreate` inserts the `uploading` row, keyed by the tus id in `assets.upload_id`, so My uploads and the "Resume N unfinished uploads" banner come from the server instead of one browser's localStorage. The hourly cleanup deletes `uploading` rows and their tus files after 48 hours.
- **Ready items stay ready during re-processing.** Re-processing, a curve override or a tier change never takes a ready item offline. The job writes into a fresh output directory (`r{rev}/` under the asset directory), then swaps the rendition rows and bumps `rendition_rev` in one transaction, then deletes the old directory. Viewers keep playing the old outputs until the swap. Core members and admins see a "processing" badge, derived from the job, while it runs.
- **Tier changes take effect at once.** A member → core change hides the item from members immediately, because `access()` reads the tier, not the files.
- **What "Process anyway" does depends on the review reason:**
  - Log or unknown-transfer video: encode as SDR with bt709 tags and no tone mapping. The admin can re-process with a curve afterwards.
  - True-HDR still: Pillow converts it to 8-bit sRGB with clipping.
  - Unrecognised container: not offered; only "Keep original only" is.

/>

Unknown and disabled emails get a decoy code row. Without it, an unknown email could only ever return "expired" from verify, never "wrong code, 3 attempts left", and that difference would reveal who is registered. A decoy can never verify, because its hash matches no code and verify also re-checks `status = 'active'`.

Sessions slide: each authenticated request refreshes `expires_at` at most once an hour and `last_seen_at` at most every 5 minutes, so reads don't turn into a write per request. Logging out deletes one session row. "Sign out of all devices", and disabling a user, delete all of that user's rows.

### Resumable upload

<Mermaid
  id="seq-upload"
  caption="Upload with resume. Uppy stores the tus URL per file fingerprint in localStorage, so picking the same file again continues at the server's offset."
  source={`sequenceDiagram
  autonumber
  participant U as Uppy (Upload screen)
  participant T as API /api/uploads (tus)
  participant F as ~/media/tus
  participant D as Postgres
  U->>T: POST (Upload-Length, metadata eventId, tier, filename, filetype)
  T->>T: onIncomingRequest: requireCore, event exists, tier allowed, size ≤ 20 GiB
  T->>F: create <id> + <id>.json
  T->>D: onUploadCreate: insert asset (uploading, upload_id = <id>)

  loop 8 MiB chunks
    U->>T: PATCH Upload-Offset n (X-Requested-With: acm-media)

    T-->>U: 204 Upload-Offset n+8 MiB
  end

  T->>T: onUploadFinish: sniff first 4 KB (magic bytes) · ffprobe or image header (≤ 15 s, nice, 1 thread)
  T->>F: rename to assets/ab/<asset>/original.<ext>, delete tus files
  T->>D: asset → queued with duration, hdr, width, height · process job, one transaction
  T-->>U: final 204 + header Asset-Id
  U->>U: done screen with ETA from GET /api/uploads/mine
  Note over U,T: lost final response → HEAD/PATCH on a finished id is answered from assets.upload_id (Upload-Offset = Upload-Length, Asset-Id)`}
/>

**The final PATCH does no full pass over the file.** At the host's 30 MB/s I/O limit, hashing a 3 GB clip takes about 100 seconds, so it can't happen inside an HTTP request. The finish hook therefore only:
- sniffs the first 4 KB;
- runs a header-only probe;
- renames the file (same filesystem, so no data copy);
- commits the asset and job rows.

The probe fills `duration_s`, `hdr`, `width` and `height` straight away, which is what makes the done-screen ETA and the grid's placeholder sizes possible.

SHA-256 is the worker's first step for every job. A match within the same event sets `duplicate_of`, and the upload and My uploads screens show the duplicate warning from the next poll.

**Resume on phones.** Re-picking from the iOS photo library can change a file's name and `lastModified`, which defeats Uppy's fingerprint. So the resume banner matches re-picked files to the event's `uploading` rows by original filename and size, and continues with that row's tus id. The file input's `accept` lists `image/heic` and `video/quicktime`, so iOS sends originals instead of transcoding them. Milestone 4 checks this on a real iPhone: originals must arrive byte-identical, and HLG must survive.

### Worker runner

<Mermaid
  id="worker-loop"
  caption="One cron tick. flock makes the runner a singleton, so a 'running' job found at start is always stale."
  source={`flowchart TD
  C[cron, every minute] --> L{flock -n worker.lock}
  L -- held --> X[exit 0]
  L -- acquired --> S[reset running → queued · run_after = now + 5 min × attempts · no extra attempt]
  S --> Q[claim: attempts < max_attempts · FOR UPDATE SKIP LOCKED · ORDER BY priority DESC, created_at]
  Q -- none --> E[exit]
  Q -- job --> H[sha256 original · set duplicate_of]
  H --> K{kind}
  K -- process/reprocess image --> I[images.py → view/thumb · encrypt if core]
  K -- process/reprocess video --> V[video pipeline]
  K -- retier --> R[re-seal or unseal files · swap keys]
  K -- purge --> P[rm asset dir · delete rows]
  I & V & R & P --> O{ok?}
  O -- yes --> D[state done · asset ready · update ρ EMA]
  O -- no --> F[attempts < max? queued with backoff : failed + asset failed]
  D & F --> W{wall time > 50 min?}
  W -- no --> Q
  W -- yes --> E`}
/>

Each step writes `jobs.step` (for example "Scoring tone curves" or "Encoding 720p") and `jobs.progress`, which ffmpeg's `-progress pipe:1` provides as `out_time_ms` ÷ duration. These are the strings the queue and My uploads screens show. A child process is killed, with its process tree, after 3 × its expected cost, with a 10-minute minimum.

- **Queue order.** Image, retier and purge jobs get priority 100 and videos get 0, so photos are never stuck behind a two-hour recording. "Move to the top" sets a job's priority to the current maximum + 1. The ETA function walks jobs in exactly this claim order.
- **Attempts.** A crash costs one attempt, not two. The stale reset puts the job back with backoff and doesn't increment, and only the claim increments. Jobs at `max_attempts` are never claimed: they become `failed`, and so does their asset.
- **Cancel.** Cancelling a queued job sets it `cancelled` straight away. For a running job, the worker checks `jobs.state` every 5 seconds while a child runs; on `cancelled` it kills the process tree and deletes `tmp/`. A first-time process job then leaves its asset `failed` with the message "Cancelled by an admin". A re-process job leaves the ready asset untouched.
- **Retry** resets `attempts` to 0 and `run_after` to now. The uploader can retry through `POST /uploads/:assetId/retry`, admins through `/admin/jobs/:id/retry`.

**Outputs are versioned.** Every run writes into `assets/ab/<id>/r<rev>/` (`hls/`, `poster`, `thumb`). Finalize swaps the `renditions` rows and `rendition_rev` in one transaction and only then deletes the previous `r<rev>/`, so playback never sees a half-written ladder.

**Sampled frames.** When automatic selection runs, `select.py` also writes its 8 sampled frames as small WebPs (long edge 320) into `runs/<run_id>/`. Only the newest run's frames are kept. For core assets they are sealed as `.enc`, like every other core output, and `/admin/assets/:id/frames/:n` serves them through the same decryptor. With `tonemap_auto=false` there are no scores or frames, and Item details shows a "Fallback curve, no scores" state instead.

**File count per video** is about 2R + 3. A three-rung video costs 1 original, 1 master playlist, 3 variant playlists, 3 `data.ts` files, 1 poster and 1 thumb: 10 files whatever the length. Single-file mode combined with `-hls_key_info_file` is Milestone 0 spike 1. If hls.js won't play that combination, the fallback is normal 10-second segments, and the result goes in `docs/decisions/hls-packaging.md`.

### ETA

The handoff's formula is implemented once in `packages/core/eta.ts` and used by both the API (My uploads, the queue) and the worker (`jobs.est_seconds`):

<Code
  id="eta-code"
  filename="packages/core/src/eta.ts"
  language="ts"
  code={"export type EtaJob = { kind: 'image' | 'video'; hdr: 'sdr' | 'hlg' | 'pq' | 'unknown' | null; durationS: number | null; progress: number | null };\n\nexport function jobCost(j: EtaJob, rho: { sdr: number; hdr: number }): number {\n  if (j.kind === 'image') return 3;\n  const d = j.durationS ?? 0;\n  return j.hdr === 'hlg' || j.hdr === 'pq' ? rho.hdr * d + 60 : rho.sdr * d;\n}\n\n/** Seconds until each job finishes, in queue order (running job first, scaled by its remaining progress). */\nexport function queueEtas(ordered: EtaJob[], rho: { sdr: number; hdr: number }): number[] {\n  let t = 0;\n  return ordered.map((j) => (t += jobCost(j, rho) * (1 - (j.progress ?? 0))));\n}\n"}
/>

After each video job, the worker updates `rho_sdr` or `rho_hdr` in `app_settings` with an exponential moving average (α = 0.2) of measured *encode* time ÷ duration. Scoring time is excluded, because the fixed 60 seconds already covers it. Over time the estimates track the real host. Jobs are summed in claim order (priority, then age), the same order the worker uses.

### Security controls

- **Headers (Helmet):**
  - CSP: `default-src 'self'; media-src 'self' blob:; worker-src 'self' blob:; img-src 'self' blob: data:; font-src 'self'; style-src 'self'; frame-ancestors 'none'`. hls.js needs `blob:` for MediaSource and its worker.
  - `Referrer-Policy: same-origin`.
  - HSTS, added once AutoSSL is confirmed.
- **Log redaction.** The pino redaction paths cover `req.headers.cookie`, `set-cookie`, `body.code`, `body.email` on auth routes, and every key-bearing field. The worker never logs `params` that carry key paths.
- **Secrets.** `.env.example` ships with every variable from the handoff's §12. On the server, `shared/.env` is chmod 600. `MASTER_KEY` is also kept in the chapter's password manager.
- **Ops.** One SSH key per maintainer, cPanel 2FA, and the known Postgres 9.6 exposure, all documented in `docs/ops.md`.

- **The viewer and player are a modal route.** Opening an item from a grid pushes `/p/:assetId` with the grid as the background location: the back button closes the lightbox and the grid keeps its scroll position. A direct visit loads the asset, then its current event underneath, so links survive moving an asset to another event. My uploads and Admin link to the same URL.
- **Slugs never change.** A slug is assigned once at creation: the start date plus the ASCII-folded title (`2026-10-28-hackathon-day-1`), falling back to the date plus a short id when the title folds to nothing, as an Arabic title would. A collision gets `-2`, `-3`. Editing the title never changes the slug, so shared links keep working.
- `GET /events/:idOrSlug` accepts either form.



</Callout>

<Callout id="i18n-decision" tone="decision">

**English only in v1, built on i18n from the first screen.**
- **Strings.** Every user-visible string goes through `i18next` + `react-i18next` with ICU plurals (`{count, plural, one {# photo} other {# photos}}`), from `apps/web/src/i18n/en.json` grouped by screen. A lint rule fails the build on string literals in JSX.
- **Formatting.** Dates, numbers, sizes and durations go through `Intl` helpers in `i18n/format.ts`, keyed on the active locale.
- **Layout.** CSS uses logical properties only (`margin-inline-start`, `inset-inline-*`, `text-align: start`), as the design's `app.css` already does. Direction-dependent icons carry the `.flip` class. `<html lang dir>` is set from the locale, and filenames and emails are wrapped in `<bdi>`.
- **Adding Arabic later** means adding `ar.json`, the Vazirmatn and Noto Naskh fonts, and a language switch, with no component changes.

</Callout>

<Callout id="jpeg-decision" tone="decision">

**HEIC photos also get a JPEG copy at ingest.** `images.py` writes `download.jpg` for HEIC/HEIF originals: sRGB, quality 90, EXIF orientation applied, capture date and device kept in the metadata. It is sealed as `.enc` for core assets. It is a new rendition kind `image_jpeg`, served by `GET /media/:id/jpeg` (minimum level `download`), and the viewer shows "Download as JPEG" next to "Download original · HEIC · 3.1 MB". It costs one extra file per HEIC asset and nothing at request time.

</Callout>

Interaction details the artboards imply and the code must honor:
- **Justified grid.** Rows are computed from `width` / `height` before images load, and virtualized with `@tanstack/react-virtual` by row. The next page is fetched when the last virtual row comes within two screens of the viewport. This is how the grid stays smooth at tens of thousands of items.
- **Resume after closing the tab.** The upload screen reads Uppy's stored tus fingerprints at mount. For each one, it compares `HEAD` offsets with the event's server-side assets, and shows "Resume N unfinished uploads" when any remain. Picking the same files continues from the stored offsets.
- **Keyboard.** The lightbox traps focus. Arrow keys, I, Z and Esc are bound to the dialog element, not to `window`. Tables and tabs follow the WAI-ARIA patterns, and `prefers-reduced-motion` disables the shimmer and transitions, matching `app.css`.
- **Alt text.** Alt text falls back to "Photo from ‹event title›, ‹date›" when there is nothing better.

## Verification

- **Unit and integration (Vitest with `app.inject`).**
  - OTP lifecycle: expiry, attempts, rate limits, and identical responses for unknown emails.
  - Sessions, sliding expiry and the CSRF header.
  - The 128-case `canView` matrix.
  - Range on plain and `.enc` files, crossing chunk boundaries and the last chunk.
  - The HLS key route returns 404 for members.
  - tus: happy path, resume, wrong type rejected.
  - ETA math.
  - All of this runs against `postgres:9.6` in docker.
- **Crypto.** Round trip, tampering, truncation, chunk reordering and empty files for ACMENC01.
- **Worker.**
  - `testsrc2` fixtures: SDR 1080p landscape, portrait, VFR, no-audio, and 360p-only (the ladder skips rungs).
  - `IMG_4515.MOV` for HLG.
  - Assert the outputs exist, `master.m3u8` parses, and every variant is tagged bt709.
  - On the server, check the whole account's thread count against the 200 limit while an HDR encode and an upload run together. Measure with `ps -L -u quhosting | wc -l`; the budget is ≤ 150.
    - ffmpeg is about 40 threads: decode 2, filters 4, and 3 x264 encoders with 2 threads plus lookahead each.
    - Node API about 12 (`UV_THREADPOOL_SIZE=4`), worker Node about 10, Python about 6, and the rest is headroom for cron and SSH.
- **Python (pytest).** HEIC with a P3 profile, EXIF rotation, PNG with alpha, `.cube` generation, the hable203 acceptance test, and `pytest -m validation` for the selection gate.
- **UI.** Playwright at 390px and 1440px in both themes, covering flows 1–7 from the design handoff against a seeded local stack. Includes axe checks for WCAG 2.2 AA contrast and keyboard-only passes through the lightbox, player, grids and tables.
- **Production smoke (`scripts/smoke.ts`).**
  1. Sign in as a seeded test member by reading the OTP over IMAP from a dedicated `smoke@qu.acm.org` mailbox on the same account. Production has no auth bypass. All smoke data lives in one "Smoke test" event that the script purges at the end.
  2. Upload a 5-second HLG clip and a HEIC photo as core.
  3. Poll until both are `ready`.
  4. Fetch `master.m3u8` and a byte range of `data.ts`.
  5. Download the original with `Range: bytes=0-99`.
  6. Confirm that a member session gets 404 for a core asset, its media and its key.
  7. Check on disk that the core asset's files end in `.enc` and that `~/keys` is empty.
