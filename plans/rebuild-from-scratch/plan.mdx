# Rebuilding the ACM Media Library for student maintainers

**Objective.** Rewrite the library so that a second-year student who has never seen it can understand the whole system in an afternoon and change one part safely in a week. The product does not change: signed-out visitors browse Public photos and videos, core members sign in with an emailed code and see encrypted core-tier items, and admins run members, events, the processing queue and storage. What changes is how the code is arranged and explained.

**The approach in one sentence.** Keep every decision that is expensive to undo (database schema, files on disk, encryption format, URLs, environment variables), and rebuild the code around it as three small TypeScript packages and one Python package, organised by feature, with short files, descriptive names, very few comments, and a README in every folder that holds a real subsystem.

**Done means:**
- The root `README.md` explains the whole system with diagrams, and links to 15 subsystem READMEs that each explain one part at the level of tables, byte layouts and state machines.
- No source file is over 200 lines. Comments only say *why* in one line where code cannot; the longer reasons are in the folder's README.
- The new code runs on the production database and `~/media` folder without a data migration, and the previous release can still be restored by flipping the `current` symlink.
- Every existing test (Vitest for api, worker and core; pytest for `mediaworker`) is ported and green, plus an API parity check against the current release and the one-event smoke test.

A few decisions are still open; they are in **Open Questions** at the bottom with a recommended default for each.

### A new maintainer's first hour

Sara joins the chapter's tech team in September. She opens the repo on GitHub and the root README is the first thing she sees. It starts with one paragraph about what the library is, then a system diagram (the one below), then "the life of a photo": upload in the browser, tus chunks into `~/media/tus`, ingest writes an `assets` row and a `jobs` row, the cron worker runs `mediaworker` to make WebP copies, and the API serves them through one access check. Each step is a link.

She is asked to fix a bug where a core video's poster shows up for a signed-out visitor. The root README's "where things live" table sends her to `server/src/access/README.md`, which has the full access matrix as a table and explains the 404-never-403 rule. The code next to it is two files of about 40 lines each with no header essay, because the README already said why. She adds a row to `access.test.ts`, which is in the same folder, and fixes the bug. She never had to read the encryption or video code.

## What stays exactly the same

<Callout id="keep-bets" tone="decision">

**The rewrite keeps every contract that production data or other people depend on.** It reuses the current database schema (migrations `0000` to `0002` copied verbatim as the baseline), the `~/media/assets/<shard>/<id>/` layout, the ACMENC01 file format and wrapped keys, the HLS packaging, every URL a user may have bookmarked or shared, the session cookie, and the names in `shared/.env`. That is what makes the rewrite deployable as an ordinary release and reversible with `scripts/deploy.sh --rollback <sha>`.

## Target repo layout

Today there are four TypeScript workspaces (`packages/core`, `apps/api`, `apps/worker`, `apps/web`) and a rule in `CLAUDE.md` that the web app may only import some folders of `core`. The rewrite has three: `shared` is the browser-safe part of today's `core`, `server` is the API and the worker together (they already share the database, crypto, paths and config), and `web` is the SPA. The import rule becomes a package boundary, so nobody has to remember it.

Inside `server/src`, code is grouped **by feature, not by layer**: everything about uploads is in `uploads/`, with its routes, its logic, its tests and its README side by side. Students fix bugs by feature ("uploads stall"), so the folder they open should hold the whole feature.

## The README system

There are three levels, and each level answers a different question. The root answers *what is this and how do the parts fit*. A package README answers *how is this package organised and how do I run it*. A subsystem README answers *exactly how does this one mechanism work and what will break if I change it*. A reader goes down only as far as the task needs.

## Code style

The rules aim at one thing: a student reads a file top to bottom once and knows what it does. The *why* lives in the folder's README, so the code can stay short and the explanation does not drift away from it in a dozen header comments.

<Table
  id="style-rules"
  columns={["Rule", "Detail", "Enforced by"]}
  rows={[
    ["Small files", "Aim for under 150 lines, never over 200. One exported idea per file, file named after it.", "ESLint max-lines (warn 150, error 200)"],
    ["Descriptive names", "viewer, asset, job, not v, a, j. Functions are verbs (claimNextJob, sealFile). Booleans read as questions (isAdmin, hasAtLeast).", "Review; ESLint id-length min 2 with i, x, y allowed"],
    ["Few comments", "No file-header essays. A one-line comment only for a why the code cannot show. Anything longer goes in the README.", "Review"],
    ["Feature folders", "Routes, logic and tests for one feature sit together. Generic helpers go in server/src/http/ only when two features use them.", "Folder layout"],
    ["Tests next to code", "foo.ts has foo.test.ts beside it. Integration tests that span features live in server/test/.", "vitest include glob"],
    ["Plain data", "Pass rows and zod-parsed objects, not classes. No dependency-injection framework; a small ctx object (db, cfg, log) is passed in.", "Review"],
    ["Types at the edge", "Every HTTP body and every mediaworker reply is parsed with a zod schema from shared/. Inside, trust the types.", "Route helpers"],
    ["One kind per file", "Styles in Component.module.css, custom hooks in useX.ts, API calls in api/, query hooks in data/, pure helpers in lib/. No inline style objects.", "ESLint react/forbid-dom-props (style), review"],

import type { Asset } from '@acm/core/db';
import type { Viewer } from '@acm/core/schemas';

export const LEVELS = ['none', 'status', 'download', 'full'] as const;
export type Access = (typeof LEVELS)[number];

export type AssetForAccess = Pick<Asset, 'tier' | 'status' | 'uploaderId' | 'deletedAt'>;

export function access(v: Viewer | null, a: AssetForAccess, eventDeleted = false): Access {
  if (!v || v.status !== 'active') return 'none';
  if (a.deletedAt || eventDeleted || a.status === 'deleting') return 'none';
  if (a.tier === 'core' && v.role !== 'core') return 'none';
  if (a.status === 'ready') return 'full';
  if (a.status === 'original_only') return 'download';
  return v.isAdmin || a.uploaderId === v.id ? 'status' : 'none';
}

/** Route guard: anything below \`min\` becomes a 404. */
export const atLeast = (have: Access, min: Access) => LEVELS.indexOf(have) >= LEVELS.indexOf(min);

### One kind of thing per file

Splitting by size is not enough on its own; a file should also hold one *kind* of thing. Today the web app has 346 inline `style={{…}}` objects across 23 files, and hooks such as `useNeighbours` (Lightbox) and `useSpeed` (Upload) are defined inside the screens that use them, so a student looking for "how the lightbox finds the next photo" has to scroll past markup and styling. The rewrite gives every kind of code its own file, named so the kind is obvious from the file list alone.

The server follows the same idea inside each feature folder: `members.routes.ts` (HTTP: parse with zod, call the service, shape the reply), `members.service.ts` (the rules, no Fastify types), `members.queries.ts` (Drizzle queries only) and `members.test.ts`. A route file that contains SQL, or a query file that knows about HTTP status codes, is the server's equivalent of an inline style.

<Callout id="split-cost" tone="info">
Vite supports CSS Modules with no extra dependency, and TypeScript gets the class names through a one-line `*.module.css` declaration in `web/src/vite-env.d.ts`. The cost is more, smaller files; the feature-folder `index.ts` and the README's file table keep them navigable.
</Callout>

<Callout id="risk-parity" tone="risk">

**The main risk is a silent behaviour change** in a rule nobody wrote down, for example which statuses count toward an event's item count. The defence is to port tests before code in every phase and to run the parity script in phase 6: the current release and the new one, on the same copy of the production database, answer the same GET requests as a signed-out visitor, a core member and an admin, and the JSON must match field for field.

</Callout>

<Callout id="risk-deploy" tone="warning">

The release tree changes shape (`server/api.cjs` instead of `api/app.cjs`), so `~/apps/acm-media/app/start.cjs` must try the new path and fall back to the old one. That lets a rollback to an old release keep working without touching the Passenger registration.

</Callout>
