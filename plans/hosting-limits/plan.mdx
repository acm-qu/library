## 1. Did we hit the host limits?

### The limits

The account `quhosting` runs inside a CloudLinux LVE. Every limit applies to the **whole account**, which is shared by five sites: library.qu.acm.org, csewiki, better-schedule (a Next.js server with about 10 threads), test and qu.hosting.

<Callout id="nproc-trap" tone="risk">

**The host reports 64 CPUs** (`nproc` = 64), but the account may only use 4 cores. Any tool that sizes its thread pool from the CPU count (ffmpeg filters, torch, BLAS, OpenMP) starts about 64 threads, and each thread counts against NPROC. One uncapped tool can use a third of the 200-task budget on its own. At idle (30-10, around 13:30) the whole account runs 15 processes with 45 threads, and the library API is 1 `lsnode` process with 11 threads.

</Callout>

## 2. How the processing time ("ready by") is calculated

<Callout id="no-prod-infinity" tone="warning">

**The "response time becomes infinity" report came from the deployed site, but the many files never reached the server.** The teammate confirmed it was production. LiteSpeed's access log shows her whole session on 30-10:

- **12:23** signs in; **12:25** deletes an old event; **12:27** creates "test-event" and uploads **one photo** (1 POST → 201, 1 PATCH → 204). It is ready about a minute later: the wait for the next cron run plus 1.3 s of processing.
- **12:31–12:32** a signed-out browser reloads the site five times; **12:41** someone signs in again (likely a second device).
- After that, **no upload requests at all**, and no server errors in the window. In all of October only 3 files were ever uploaded.

So whatever looked infinite happened in the browser, before anything was sent. Likely causes:

1. **Uploader bug, fixed in 574e083.** Before a file starts, `apps/web/src/lib/uploader.ts` looks up saved resume state with `findPreviousUploads()`. That call had no error handling: if it failed (site storage blocked or full), `start()` never ran, the file sat at 0% with nothing sent, and "about N left" grew without bound. It now falls back to a fresh upload.
2. **Picking many videos on an iPhone** [inferred]. iOS converts each selected video ("Preparing…") before the page receives the file, which can take minutes with no progress shown on the page.
3. **Deploys at 12:36 and 12:44** restarted the API. Requests during a restart are retried and none failed, so this is not the cause, but each restart paused the site briefly.

**Next:** ask her whether it was on her phone, and whether files showed in the list at 0% or the picker hung on "Preparing". Since 28541d2 the upload screen says "waiting to start" or "stalled, nothing sent for 20 s", and the app says "Waiting for the processor" when the worker heartbeat is stale, instead of showing a growing number. 574e083 also stops a request to `/api/events/` with an empty id, which showed up as 404s in the same log.

</Callout>


The API orders the queue the same way the worker claims jobs (running first, then priority descending, then oldest first) and gives each job a cost in seconds. The code is `jobCost` and `queueEtas` in `packages/core/src/eta.ts:22-32`, fed by `apps/api/src/lib/queue.ts`.

```latex
\text{cost}(j)=\begin{cases}3 & \text{image}\\ \rho_{\text{sdr}}\,d & \text{SDR video}\\ \rho_{\text{hdr}}\,d + F & \text{HDR video}\end{cases}
```

Here `d` is the video's duration in seconds, and `F` is `score_seconds`: 340 when automatic tone-curve scoring (`tonemap_auto`) is on, otherwise 60. The defaults are `\rho_{\text{sdr}} = 0.6` and `\rho_{\text{hdr}} = 1.2`. The time until job `k` finishes is the sum of the remaining costs of every job ahead of it, including itself:

```latex
E_k=\sum_{i\le k}\text{cost}(j_i)\,(1-p_i)\qquad\qquad \text{ready}_k = t_{\text{now}} + E_k
```

`p_i` is the progress of the running job and is 0 for every queued job. Since 28541d2 the sum skips jobs waiting out a retry backoff (`run_after` in the future, by the database clock); they get no ETA themselves. If the worker heartbeat `worker_tick` is older than 5 min (`STALE_TICK_MS`; 5 min because cron starts the worker every 2 min), every `readyInS` is null and the app shows "Waiting for the processor". The worker now also beats every minute during long jobs. The web app shows either "ready by" `t_{\text{now}} + E_k` (`readyAt` in `apps/web/src/i18n/format.ts:37`) or `fmtEta`, which is `\max(1, \operatorname{round}(E/60))` minutes and prints a dash for a non-finite value. Both are recomputed on every 15 s poll (was 5 s). After each encode, the worker updates `\rho` with an exponential moving average (`nextRho` in `eta.ts`; `video.ts`), and `score_seconds` is learned the same way. Both are now clamped (`RHO_RANGE`, `SCORE_RANGE`):

```latex
\rho \leftarrow \operatorname{clamp}_{[0.3,\,3]}\!\Big((1-\alpha)\,\rho + \alpha\,\frac{T_{\text{encode}}}{d}\Big),\qquad F \leftarrow \operatorname{clamp}_{[60,\,900]}\big((1-\alpha)\,F + \alpha\,T_{\text{score}}\big),\qquad \alpha = 0.2
```

`\rho` is still learned from wall time, not CPU time. Production has learned `\rho_{\text{hdr}} = 1.219`.

### Wait before processing starts

The ETA above counts from the moment the worker runs. Before 73eecba a job waited for the next cron minute first. Now the API starts the worker about a second after an upload's last PATCH (`WORKER_WAKE`, see step 11), and cron (every 2 min) only covers admin actions, retries and crashes:

```latex
T_{\text{ready}} = W_{\text{start}} + E_k,\qquad W_{\text{start}} \sim U(0,\,60)\ \text{s}\ \ (\text{mean } 30\ \text{s}) \;\longrightarrow\; \begin{cases} \approx 1\ \text{s} & \text{upload}\\ U(0,\,120)\ \text{s} & \text{admin action, retry} \end{cases}
```

If a worker is already running, the job simply waits its turn in `E_k`; if one is just exiting, `flock -w 20` waits it out.

### (a) SDR photo

1. **Browser.** `apps/web/src/lib/uploader.ts:24-26` sends a tus POST, then 8 MiB PATCH chunks one after another. Up to 2 files upload in parallel, at most one of them a video (`toStart`), and failed chunks retry after 0, 1, 3, 5, 10, 20 and 30 s.
2. **API.** `apps/api/src/routes/uploads.ts` writes chunks to `MEDIA_ROOT/tus/<id>`. The last PATCH waits for `ingest()`: sniff 4 KB, probe the image (reads 2 MiB), rename to `assets/<shard>/<id>/original.ext` (a move, not a copy), then one transaction marks the asset `queued` and adds a `process` job with priority 100. Every PATCH refreshes the row's `updatedAt`, so an `uploading` row untouched for an hour no longer counts as active. The API does no hashing.
3. **Worker.** Right after ingest the API runs `WORKER_WAKE` (`apps/api/src/lib/wake.ts`: the crontab's command with `flock -w 20`, in its own process group), so `apps/worker/src/runner.ts` starts in about a second. Cron (every 2 min, `flock -n`) is the fallback. It claims the job and sets `processing`. `jobs/process.ts` computes a sha256 of the whole original the first time it runs; duplicates are flagged with `duplicate_of` but still processed.
4. **Python.** `mediaworker images` (nice 19 under `ionice -c3`, `THREAD_ENV`, 180 s timeout) fully decodes the image with Pillow (HEIC through pillow_heif, 4 decode threads), applies EXIF rotation, converts ICC to sRGB, and writes `view.webp` (2560 px, q82) and `thumb.webp` (480 px, q75).
5. **Publish.** Core tier: `sealAll` encrypts both WebP files. Publish renames tmp → `r<rev>`. `reconcileOriginal` reads the original and writes it to `.enc` for core tier, then deletes the plaintext. After the pass, `storageStatsIfStale` walks the whole `MEDIA_ROOT` tree, but only if the last walk is older than 15 min (`apps/worker/src/run.ts`, `stats.ts`). ETA cost: 3 s.

### (b) HDR photo

A still image with an nclx PQ or HLG transfer (16 or 18) is decoded, then stopped in `needs_review` with reason `hdr_still`. An admin's "Process anyway" clips it to 8-bit without tone mapping and continues as in (a). iPhone gain-map HEIC files are not PQ/HLG, so they follow path (a) directly (inferred).

### (c) SDR video

1. **Upload and ingest** as in (a), except that ingest runs `ffprobe -threads 1` inside the request (20 s timeout, `apps/api/src/uploads/probe.ts`) and the job's priority is 0.
2. **Classify.** The worker runs `ffprobe -threads 1` (60 s). An unknown transfer, or 10-bit without tags, goes to `needs_review`.
3. **Ladder.** One ffmpeg (`apps/worker/src/lib/ffmpeg.ts:124-129`) encodes every rung: 360p CRF26 1M/96k, 720p CRF23 3M/128k, 1080p CRF22 6M/128k, never upscaled. Since 28541d2 it uses one thread per stage: decoder `-threads 1`, `-filter_threads 1` and `-filter_complex_threads 1`, and libx264 veryfast `-threads 1` per rung (3 rungs, about 3 cores), and writes single-file HLS with 6 s segments. Timeout: `\max(15\,\text{min},\,4\,\text{s}\times d)`. Core tier: ffmpeg applies HLS AES-128 encryption.
4. **Poster.** A second ffmpeg seeks to 10% with `-filter_threads 1`, input `-threads 1` and output `-threads 1` (before 28541d2 the filter threads were uncapped and defaulted to the CPU count of 64, inferred). Python then makes `poster.webp` and `thumb.webp`, which are sealed for core tier.
5. **Publish**, then update `\rho_{\text{sdr}}`, encrypt the original for core tier, and walk storage.

### (d) HDR video (HLG/PQ, e.g. iPhone)

As (c), with a tone-map curve chosen first: an admin override wins. If `tonemap_auto` is off (production today: no `tonemap_auto` row), the curve is `hable203` through zscale+tonemap (no LUT). With auto on (the admin checkbox; the validation gate no longer blocks it), the worker builds the LUTs once, then runs Python `select`:
- a keyframe scan of the **whole file** (ffmpeg `-filter_threads 1`, decoder `-threads 2`, output `-threads 1`);
- 8 frames extracted, one ffmpeg each, with the same caps (`THREADS` in `frames.py`);
- each frame scored on 4 curves × 2 metrics with pyiqa DISTS + TOPIQ-FR on CPU (`torch.set_num_threads(2)`), loading about 0.6 GB of weights on every run.

This was measured at **5.6 min and 1.9 GB RSS per video** (`docs/decisions/tone-curves.md:32`). If it fails, the worker falls back to `hable203`. Tone mapping runs at full source resolution in float32 before the split into rungs. Timeout: `\max(15\,\text{min},\,8\,\text{s}\times d)`.

### (e) 10 files at once

The browser uploads 2 at a time, at most one video. Each finished file adds 1 job and wakes the worker (a running worker just picks it up). Photos (priority 100) go ahead of every queued video (priority 0), even videos that were queued first. The worker runs the jobs one at a time, possibly over several passes (each has a 50 min deadline), and then does at most one storage walk per 15 min. During the batch, each visible tab polls `/uploads/mine` every 15 s, and each poll runs about 6 SQL queries, including `activeJobs`, which scans the whole queue.

## 4. Models: operations → processes, CPU, disk

### 4.1 Processes (NPROC counts processes + threads)

```latex
N(t) = N_{\text{other}}(t) + L\,N_{\text{api}} + N_{\text{cron}}(t) + \sum_{j \in \text{running}(t)} N_{\text{job}}(j) + N_{\text{deploy}}(t) \le 200
```

- `N_{\text{other}}`: the other 4 sites, measured at about 20–30 at idle (better-schedule alone is about 10).
- `N_{\text{api}} \approx 1 + 4_{\text{libuv}} + 6_{\text{V8}} \approx 11` per `lsnode` instance. `L` is the number of instances: 1 observed (step 9); the 5 process ids seen in one hour were restarts, one per deploy.
- `N_{\text{cron}} \approx 2` (sh + flock) `+\,10` (worker node) while the worker runs, plus 10 for each overlapping cleanup or stats node. Each `WORKER_WAKE` that finds the worker busy adds about 2 (sh + flock) for up to 20 s; with 2 uploads in parallel that is at most about 4.

Child processes per job:

```latex
N_{\text{image}} = 1 + 4\,h \qquad (h = 1 \text{ for HEIC decode threads})
```

```latex
N_{\text{encode}} = 1 + T_{\text{dec}} + T_{\text{filter}} + \sum_{r=1}^{R} (T_{\text{x264}} + a) \approx 1 + 1 + 1 + 3\,(1 + a) \qquad [\text{was } 1 + 2 + 2 + R\,(2 + a)]
```

with `R \le 3` rungs and `a \approx 2\text{–}4` x264 helper threads for lookahead and similar work (inferred), which gives about 12–18 since 28541d2 (17–23 before); the worker node is counted in `N_{\text{cron}}`.

```latex
N_{\text{poster}} = 1 + T_{\text{dec}} + T_{\text{filter}} = 1 + 1 + 1 = 3 \qquad [\text{was } 1 + 2 + C,\; C = \text{nproc} = 64 \;\Rightarrow\; \approx 67,\ \text{inferred}]
```

```latex
N_{\text{select}} = 1 + T_{\text{torch}} + T_{\text{omp}} + N_{\text{ffmpeg child}} \approx 1 + 2 + 2 + (1 + 2 + 1 + 1) \approx 10 \qquad [\text{was } 1 + 2 + 2 + (1 + C)]
```

A deploy before the BLAS cap started `N_{\text{deploy}} \approx k \cdot C` threads (several pools of 64 each), which caused the 120 faults. After the cap, BLAS uses 1 thread and OpenMP uses 2, and since 28541d2 a deploy only builds the venv and runs the gate when `py/` changed. The worst realistic case before the caps (the poster step), and after them, where the poster step drops to about 56 and the ladder encode becomes the peak:

```latex
N \approx 30 + 11 + 12 + 67 = 120 \qquad\longrightarrow\qquad N_{\text{poster}}:\ 30 + 11 + 12 + 3 \approx 56, \qquad N_{\text{encode}}:\ 30 + 11 + 12 + 18 \approx 71
```

### 4.2 CPU (SPEED limit = 4 cores = 400%)

The demanded parallelism is the number of busy threads, `D(t) = \sum_i u_i(t)`. The whole account is granted `\min(D, 4)`. Nice does not raise the account quota; it only orders our own threads. Worker children now run at nice 19 under `ionice -c3` (verified on the server), and so does deploy work. A job that needs `W` CPU-seconds of work takes this long:

```latex
T_{\text{wall}} = \frac{W}{\min\!\big(D_{\text{job}},\; 4 - D_{\text{rest}}\big)}
```

A 1080p ladder encode demands `T_{\text{dec}} + T_{\text{filter}} + R\,T_{\text{x264}} = 1 + 1 + 3\cdot 1 = 5` since 28541d2 (it was `2 + 2 + 3\cdot 2 = 10`), still a little over 4, but at nice 19 the API wins whenever it needs a core. The API runs on a single Node event loop and competes for the same 4 cores, so its latency rises (M/M/1 approximation):

```latex
R_{\text{api}} \approx \frac{1}{\mu_{\text{api}} - \lambda_{\text{api}}}, \qquad \mu_{\text{api}} \propto \frac{4 - D_{\text{worker}}}{4}
```

The request rate `\lambda_{\text{api}}` comes from polling and PATCHes:

```latex
\lambda_{\text{poll}} = \frac{n_{\text{visible polls}}}{15\,\text{s}}, \qquad \lambda_{\text{patch}} = \frac{2\,v_{\uparrow}}{8\,\text{MiB}}
```

For example, 5 visible polls make 20 requests/min (60 at the old 5 s interval), and 2 parallel files at `v_{\uparrow} = 20\,\text{Mb/s} \approx 2.5\,\text{MB/s}` each add about 37 requests/min. Measured encode time is `T \approx \rho\, d` with `\rho_{\text{sdr}} = 0.6` and `\rho_{\text{hdr}} = 1.2` (production has learned 1.219), plus 340 s of scoring when auto is on. One thread per rung makes encodes slower in wall time, so `\rho` may drift up; the clamp bounds it at 3.

### 4.3 Disk IO (30 MB/s for the whole account)

Bytes moved for one original of size `S`, with `c = 1` for core tier and `a = 1` for auto-HDR scoring:

```latex
B_{\text{photo}} = \underbrace{S}_{\text{upload write}} + \underbrace{S}_{\text{sha256}} + \underbrace{S}_{\text{decode}} + \underbrace{O_{\text{img}}}_{\text{WebP} \,\approx\, 0.05\text{–}0.1\,S} + c\,(2S)
```

```latex
B_{\text{video}} = S\,(3 + a + 2c) + O_{\text{hls}}, \qquad O_{\text{hls}} \le d \cdot \frac{(1 + 3 + 6)\,\text{Mb/s}}{8} = 1.25\,d \;\text{MB}
```

```latex
t_{\text{IO}} \ge \frac{B}{30\,\text{MB/s}}
```

For example, a 1 GB core-tier HDR clip with auto scoring and `d = 120\,\text{s}` gives `B = 1\cdot(3+1+2) + 0.15 = 6.15\,\text{GB}`, so `t_{\text{IO}} \ge 205\,\text{s}` even with nothing else on the disk. Two parallel uploads at 20 Mb/s each write 5 MB/s, which is 17% of the cap. A fast uplink (2 × 100 Mb/s = 25 MB/s) nearly fills the cap by itself. A deploy (npm install, pip, reading 0.6 GB of torch weights) spends tens of seconds at the cap; the 30-10 IO faults line up with the 4 deploys that reached the server (1 at 11:00, 3 at 12:00). Since 28541d2 a deploy hashes `py/`, the venv script and the gate into `shared/.py-hash` and skips the venv, the weights and the gate when nothing changed, and runs at nice 19 under `ionice -c3`. After a pass, at most every 15 min, the storage walk makes about `3\,n_{\text{photo}} + 10\,n_{\text{video}}` stat calls (plus 8 frames per auto-HDR video). That is metadata IO: fine when the cache is warm, seconds when it is cold (inferred).

### Step 2: keep the worker under 3 of the 4 cores (done, 28541d2)

The HLS encode in `apps/worker/src/lib/ffmpeg.ts` (`hlsArgs`) now uses one thread per stage: decoder `-threads 1`, `-filter_threads 1` and `-filter_complex_threads 1`, and libx264 `-threads 1` per rung (3 rungs, about 3 cores). ### Step 3: automatic tone-curve selection as an admin checkbox (done, 28541d2)

Automatic selection is now a checkbox in **Admin › Storage** that takes effect as soon as it is ticked. The validation gate no longer blocks it: its result is shown next to the checkbox as information only ("Validation passed on the server" or "hasn't run yet"). The API falls back to off when the setting is unset, and per-video admin overrides still win. **Production has it off** (there is no `tonemap_auto` row), so HDR videos use `hable203`, saving 5.6 min, 1.9 GB of RAM and a full extra read per HDR video. ### Step 4: stop doing heavy work on every deploy (done, 28541d2)

`scripts/deploy.sh` hashes `py/`, `deploy/setup-worker-venv.sh` and the gate into `shared/.py-hash`, and runs the venv setup, the scorer weights and the tonemap gate only when that hash changed. The new hash is written only after the gate succeeds. All deploy work (npm install, venv, migrate, gate) runs at nice 19 under `ionice -c3`. `setup-worker-venv.sh` no longer uses `pip --upgrade`, and the gate now reuses a failed result too (same fingerprint), and reads torch/pyiqa versions from package metadata instead of importing torch. ### Step 5: throttle the storage walk (done, 28541d2)

`apps/worker/src/run.ts` now calls `storageStatsIfStale` (`apps/worker/src/stats.ts`), which walks `MEDIA_ROOT` only when the last measurement is older than 15 min. The nightly walk is unchanged.

`refetchInterval` in `apps/web/src/data/uploads.ts`, `library.ts` and `admin.ts` (and the shell's chip) is 15 s instead of 5 s. - `apps/api/src/lib/queue.ts` gives no ETA to jobs in retry backoff and leaves them out of the others' sums. `ps` shows 1 `lsnode` instance. The 5 process ids in one hour are restarts (deploys `pkill lsnode`), not parallel instances, so nothing needed pinning.

### Step 10: monitoring (done, 28541d2)

The spawn helpers sample each child's thread count (its whole process group for Python), and `apps/worker/src/runner.ts` logs `peakThreads` in each "job done" line. `deploy/health.sh` mails once when the worker has not checked in for 10 minutes, and once more when it is back. Per-job CPU time is not logged.

### Step 11: start the worker when an upload finishes (done, 73eecba)

Processing now starts about a second after an upload instead of up to a minute later. Cron moves to every 2 minutes (changed by hand in cPanel; `deploy/crontab.template` and `docs/ops.md` updated) and still covers admin actions, retries, crashes and the 50-min deadline. Unset, the library falls back to cron only.

### Step 12: a hard budget for every step of uploading and playing videos (done, 201e416)

The account's limits are shared by every site on it, so each step gets a fixed share instead of relying on the steps never overlapping. The target is that the worst case, with everything running at once, stays at or under about 70% of every limit (SPEED 400%, PMEM 4 GB, IO 30 MB/s, NPROC 200, EP 150):

```latex
\text{IO}_{\max} = \underbrace{5}_{\text{uploads}} + \underbrace{8}_{\text{worker}} + \underbrace{5 + 3}_{\text{serving}} = 21\ \text{MiB/s} \approx 70\%\ \text{of}\ 30\ \text{MiB/s}
\qquad
\text{CPU}_{\max} \approx \underbrace{200\%}_{\text{worker}} + \underbrace{50\%}_{\text{API}} \approx 250\% \approx 64\%\ \text{of}\ 400\%
```

The hash/seal step and the encode never run at the same time (the worker does one step after another), so the worker's share is the larger of the two, 8 MiB/s. The IO total is 70% if the host's MB/s means MiB/s, as LVE's KB/s settings suggest, and 73% (22 MB/s) if it means `10^6` bytes. Other limits:

- **Entry processes (150):** at most 32 paced large responses are held at once (`MAX_PACED`); the 33rd gets a 429 before any header is sent. Paced streams buffer one chunk, not 16, so a slow client holds little memory.
- **Processes (200):** the API keeps at most one `WORKER_WAKE` waiter alive (apps/api/src/lib/wake.ts), so a batch of uploads no longer starts one 20-second `flock` per file. Torch uses one inter-op thread (`set_num_interop_threads(1)`).
- **Memory (4 GB):** Pillow refuses images over 120 MP (`MAX_IMAGE_PIXELS = 60_000_000`, which Pillow enforces at 2×), so one decode stays around 1.1-1.4 GB. HDR tone-mapping now works on frames of at most 1080p instead of full 4K float RGB.
- **Ingest probe:** the API's ffprobe at upload finish runs at nice 19.
- **Backups:** `deploy/backup.sh` reads only `DATABASE_URL` from `shared/.env` instead of sourcing it (sourcing failed on the `SMTP_PASS` line, so `~/backups` was empty), and dumps at nice 19 under `ionice -c3`.

Costs: hashing a 150 MB video takes about 18 s instead of 2; an encode of a source above 5 MiB/s (for example 4K at 100 Mb/s) runs no faster than about 0.4× real time, and on 2 cores a 1080p ladder encodes slower than before; one 1080p stream needs about 0.75 MB/s, so about 7 people can start videos at the same moment before playback waits on the 5 MiB/s budget (repeat views come from memory and cost nothing). Two uploads at once now share 5 MiB/s instead of getting 5 each. A job queued while a woken worker is exiting waits for the next cron run, at most 2 minutes.
